# Template-Based PageSpeed Advisor

Internal tool for **Deccan Herald (DH)** and **Prajavani (PV)**. It measures Lighthouse **performance** and **accessibility** per CMS **page template** (not per URL), explains what to fix with an evidence-bound LLM, and ranks the fixes with a score computed in code.

```
Brand -> Template -> 5-10 sample URLs -> PageSpeed Insights + CrUX -> aggregation per template
      -> LLM (evidence only) -> schema + grounding validation -> priority ranking -> web UI
```

> **Apps Script source is admin-only. Normal developers use only the web UI.**
> Developers never see the Apps Script editor, Script Properties, API keys, triggers or the endpoint URL.

## Architecture

| Tier | What | Where |
|---|---|---|
| Data layer | Scheduler, PSI + CrUX collector, Sheets/Drive storage, per-template aggregation, resumable queue, token-protected JSON endpoint | `apps-script/` (runs in Google, managed by the admin) |
| Backend | Reads aggregates, calls the LLM, validates output, computes priority, enforces login and roles | Next.js route handlers + `lib/` |
| Web UI | Template overview, template detail (ranked fixes + evidence), run history, admin status | `app/`, `components/` |

Numbers are always computed in code. The LLM only explains and proposes; it sees only the aggregated evidence, and anything it says that the evidence does not back is dropped before it reaches the UI.

## Quick start (local demo, no Google account needed)

Prerequisites: **Node.js 20 or newer** (tested on 22) and npm.

```bash
npm install
cp .env.example .env.local           # then edit it, see below
npm run hash-password                # once per user; paste the output into AUTH_USERS
npm run dev                          # http://localhost:3000
```

In `.env.local` set at minimum:

```
DATA_SOURCE=mock
SESSION_SECRET=<48 random chars: node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))">
AUTH_USERS='[{"username":"admin","role":"ADMIN","passwordHash":"scrypt:..."},{"username":"dev","role":"DEVELOPER","passwordHash":"scrypt:..."}]'
AI_PROVIDER=mock                      # optional offline stand-in so "ranked fixes" works without an API key
```

Mock mode shows **synthetic** data (bannered in the UI) generated by the real aggregation code, with history and one "after a fix" re-test, so every screen can be explored.

## Roles

| | ADMIN | DEVELOPER |
|---|---|---|
| Template overview, template detail, ranked fixes, run history | yes | yes |
| Queue a re-test of the same sample URLs | yes | yes (unless `ALLOW_DEVELOPER_RETEST=false`) |
| `/admin` and `/api/admin/*` (system status, registry view, URL-to-template check) | yes | **no (403)** |
| Apps Script editor, Script Properties, triggers, deployment | only the Apps Script owner | **never; not reachable from the web app** |

Enforced twice: `middleware.ts` (session + admin paths) and every route handler (`lib/auth/guard.ts`). Sessions are signed, httpOnly, 8 hours. State-changing requests check `Origin`. Login is rate-limited per IP + username (in memory, per server instance).

PRD open question 4 asks about SSO. This build uses local accounts so it runs anywhere; replace `lib/auth/users.ts` and the login route when SSO is decided.

## Admin setup: Google Apps Script (data layer)

Only an admin does this.

### 1. Spreadsheet and project
1. Create a Google Sheet; copy its ID from the URL (`/spreadsheets/d/<ID>/edit`).
2. **Extensions > Apps Script** (project owned by an admin account; do not share it with developers).
3. **Project Settings**: tick *Show "appsscript.json" manifest file*, then replace its contents with `apps-script/appsscript.json`.
4. Add one script file per `apps-script/*.gs` and paste the contents: `Config.gs`, `Templates.gs`, `PageSpeed.gs`, `Crux.gs`, `Storage.gs`, `Aggregation.gs`, `Queue.gs`, `WebApp.gs`. They share one global scope, so do not rename functions. Delete the default `Code.gs`.

### 2. Script Properties (Project Settings > Script Properties)
| Property | Required | Meaning |
|---|---|---|
| `SPREADSHEET_ID` | yes | The sheet from step 1 |
| `PAGESPEED_API_KEY` | yes | Google API key with the **PageSpeed Insights API** enabled (restrict it to the APIs it needs) |
| `API_TOKEN` | yes | Long random string; the web app sends the same value as `APPS_SCRIPT_TOKEN` |
| `CRUX_API_KEY` | no | Key with the **Chrome UX Report API** enabled; if empty, `PAGESPEED_API_KEY` is used (enable both APIs on it) |
| `DRIVE_FOLDER_ID` | no | Folder for raw Lighthouse JSON; if empty one is created |
| `RUNS_PER_URL` | no | PSI runs per URL, median used (default 3) |
| `RETEST_COOLDOWN_MINUTES` | no | Gap between re-tests of one template+device (default 30) |
| `DAILY_HOUR` | no | Hour of the daily schedule in the script time zone (default 2) |
| `BRAND_HOSTS` | no | JSON host allow-list, default `{"DH":["www.deccanherald.com"],"PV":["www.prajavani.net"]}` |
| `TIME_BUDGET_MS`, `MIN_REMAINING_MS`, `MAX_AUDITS_PER_AGGREGATE`, `FAIL_THRESHOLD`, `RAW_RETENTION_DAYS` | no | Tuning (defaults 240000, 70000, 40, 0.9, 30) |

API keys are stored only here: never in the repo, the browser, the Next.js app, the sheet, or any API response.

### 3. Create the tabs
In the editor choose `setup` and **Run** (authorize the scopes once). Tabs and columns:

* **Templates**: `template_id | template_name | brand | url_pattern | sample_urls | active | traffic_weight | notes`
* **Runs**: `run_id | created_at | started_at | finished_at | trigger | requested_by | brand | template_id | device | status | url_count | units_done | units_failed | summary_json | error`
* **Audits**: one row per URL x run: scores, lab metrics, CrUX p75, `drive_file_id`, trimmed failing audits as JSON (max 45,000 chars per cell)
* **Aggregates**: one row per finished run (template x device): headline numbers plus the `aggregate_json` the web app reads

Full Lighthouse JSON is stored gzipped in Drive, never in cells. Files older than `RAW_RETENTION_DAYS` are trashed by a daily trigger.

### 4. Template registry
Fill the **Templates** tab (see `apps-script/templates.example.csv`). It is the single source of truth and is edited **only in the sheet**:

* `template_id`: `UPPER_SNAKE_CASE`, e.g. `DH_ARTICLE`
* `url_pattern`: path pattern; `*` = within one path segment, `**` = across segments, `/` = home page only
* `sample_urls`: 5 to 10 https URLs, one per line in the cell, on the brand's allowed host, matching the pattern
* `active`: `TRUE`/`FALSE`; `traffic_weight`: blank = equal weight (PRD: equal until per-template GA4 share exists)

Rows that fail validation are never measured; `/admin` shows why. The real inventory (and whether Quintype exposes a template name per story) is PRD Gate 0 and is deliberately not hard-coded. A "Home" template normally has one canonical URL while the PRD asks for 5 to 10 samples, so decide how to sample it.

### 5. Triggers
Run `installTriggers` once. It creates `scheduleDailyRun` (daily at `DAILY_HOUR`; queues every active valid template for mobile and desktop), `processQueue` (every 5 minutes) and `purgeOldRawFiles` (daily). To start immediately run `scheduleDailyRun` once; the 5-minute trigger processes the queue.

**Resumable queue:** the queue lives in Script Properties. Each execution stops starting new URLs after about 4 minutes and saves its position after every URL; the next trigger continues from the next URL, nothing restarts. If PSI is rate limited the same URL is retried on later triggers (5 attempts, then it is recorded as failed).

**Quota:** Apps Script caps total trigger runtime per day (about 90 min on consumer accounts, 6 h on Workspace). A URL takes roughly 20 to 40 s (its runs execute in parallel). Rough daily cost = templates x 2 devices x sample URLs x ~30 s; for example 8 templates x 2 x 8 URLs is about 64 min. Use a Workspace account or fewer templates/URLs/runs if needed. Aggregation reads the whole Audits tab; PRD risk 5 (move history to Aurora PostgreSQL) applies as it grows.

### 6. Deploy the web endpoint
**Deploy > New deployment > Web app**: *Execute as* **Me**, *Who has access* **Anyone**; copy the `/exec` URL. "Anyone" is needed because the Next.js server cannot sign in with a Google account; access is controlled by `API_TOKEN` and the URL is never shown to developers. After code changes: **Deploy > Manage deployments > Edit > New version**.

* Data actions are `POST` with the token in the JSON body (not the URL, so it stays out of logs). `GET` returns only a liveness marker. (This differs from the PRD's `doGet` on purpose.)
* Actions: `health`, `templates`, `aggregates`, `aggregate-history`, `runs`, `retest`. A wrong token returns `UNAUTHORIZED` and no data.
* `retest` accepts only a template id and device; URLs always come from the Templates sheet.

### 7. Connect the web app
Set `DATA_SOURCE=apps-script`, `APPS_SCRIPT_ENDPOINT=<the /exec URL>`, `APPS_SCRIPT_TOKEN=<API_TOKEN value>`. The endpoint must be `https://script.google.com/...`. Open `/admin` as an admin to check the connection and registry. To rotate, change `API_TOKEN` and `APPS_SCRIPT_TOKEN` together.

### 8. LLM
Set `AI_PROVIDER` (`anthropic`, `openai`, `gemini`, `ollama`) and its key. The model receives only the aggregated evidence plus a fixed stack context (`lib/llm/prompt.ts`). Hosting and provider are PRD open question 2; the code is provider-agnostic.

## How numbers and fixes work

* **Per URL:** PSI runs `RUNS_PER_URL` times per device; the median-performance run represents the URL.
* **Per template + device (`Aggregation.gs`):** median performance and accessibility, median lab metrics, CrUX p75 (URL-level if available, else origin-level, else none), and for each failing audit: affected URL count and share, median savings (ms or bytes), repeated offenders (same script/image/stylesheet on 2+ URLs), representative URLs. There is no custom health score.
* **LLM output (strict schema):** `issue, audit_ids, affected_urls, likely_cause, proposed_change, effort (S|M|L), confidence (High|Medium|Low), verify_step`; unknown keys are rejected.
* **Grounding (`lib/validation/grounding.ts`), any failure drops the issue:** audit ids must exist in the input; URLs must be in the sample set and flagged by a cited audit; every number in the text must derive from the input; schema must validate. Rejections are listed in the UI so reviewers can judge the model (PRD Gate 2). When evidence does not support a cause the model must say `unknown`.
* **Priority (`lib/priority`):** `median savings x share of URLs x traffic weight / effort`, S=1, M=2, L=4. Byte-only savings convert to ms with Lighthouse's default throttling (mobile 1,638.4 Kbps, desktop 10,240 Kbps). For an issue citing several audits the largest savings and share are used (no double counting). Audits with no measured savings (layout shifts, most accessibility audits) show as "not quantified" and rank after quantified ones; nothing is invented.
* **Overview "Top issue":** the failing Lighthouse audit with the highest measured impact (deterministic, no LLM call per row). The LLM fix list is on the detail screen.

## Re-test after a fix
On the template page click **Re-test same sample URLs** (per device). This queues a run of exactly the registered URLs; the next 5-minute trigger processes it (watch Run history). When done, the detail page compares the latest run with the previous one: score deltas and, per audit, affected URLs before and after. It is a measured comparison only; there are no alerts.

## API (session cookie required; JSON)

| Endpoint | Role | Purpose |
|---|---|---|
| `POST /api/auth/login`, `POST /api/auth/logout` | public | Sign in / out |
| `GET /api/templates?brand=&device=` | any | Overview rows, lowest performance first |
| `GET /api/templates/:id?device=` | any | Latest aggregate, history, comparison |
| `POST /api/templates/:id/analysis` `{device}` | any | Validated, ranked fixes (cached per run; 20/min per user) |
| `GET /api/runs?brand=&templateId=` | any | Run history |
| `POST /api/retest` `{templateId, device: mobile\|desktop\|both}` | any (admin only if `ALLOW_DEVELOPER_RETEST=false`) | Queue a re-test |
| `GET /api/admin/config`, `GET /api/admin/registry`, `POST /api/admin/match-url` | ADMIN | Config presence (no secrets), registry with problems, URL-to-template check |

Errors: `{ "error": { "code", "message" } }` with 400/401/403/404/429/502. The browser never calls PageSpeed, CrUX, Apps Script or the LLM directly.

## Security notes
* No secrets in the repo; `.env.local` is git-ignored; `.env.example` has placeholders only.
* The app never fetches user-supplied URLs. Sample URLs come from the registry, must be https, without credentials or ports, and on a brand host (checked in the app and in Apps Script). The admin URL matcher is pure string logic.
* Apps Script writes cells with formula-injection protection.
* Login rate limiting and the analysis cache are per server instance (on serverless hosting they reset between instances).
* **If the previous `.env.local` was shared anywhere, rotate those PageSpeed/LLM keys.**

## Hosting notes
The analysis route allows up to 60 s (`maxDuration`); plans with shorter limits can cut LLM calls short. On Vercel set the same variables in project settings.

## Troubleshooting
| Symptom | Likely cause |
|---|---|
| "server is not configured for sign-in" | `SESSION_SECRET` missing or under 32 chars |
| Nobody can sign in | `AUTH_USERS` missing or invalid JSON (wrap in single quotes) |
| "data service did not return JSON" | Deployment access is not **Anyone**, or an old version is deployed |
| `UNAUTHORIZED` from the data service | `APPS_SCRIPT_TOKEN` differs from `API_TOKEN` |
| Overview empty | No finished run yet: run `scheduleDailyRun`, wait for `processQueue`, check the Runs tab |
| Template never measured | Row invalid or inactive; see `/admin` |
| Runs stay `queued` | `processQueue` trigger missing (`installTriggers`) |
| Many failed URLs | PSI quota or key restrictions; confirm the API is enabled on the key |
| "No LLM configured" | `AI_PROVIDER` or its key is missing |
| Suggestions rejected | Expected when the model cites something outside the evidence; the UI lists why |
